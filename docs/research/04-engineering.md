# Agent 工程案例：如何知道一轮修改已经成功

课程的难点集中在两个时刻：用户还没有确认关键条件，以及几何引擎返回了一个有效、但没满足需求的实体。下面用公开工程实践讨论这些时刻需要什么数据、谁能作出判断。核查日期为 2026-11-25。引用的系统均未在本次工程调研中部署。

## 从零搭起一个能持续工作的循环

**已核实·源码。** Anthropic 的 autonomous-coding 示例把首次初始化和后续增量工作写进一个可读入口。固定提交中，`run_autonomous_agent` 查看项目目录中是否已有 `feature_list.json`，选择相应提示词，创建客户端并调用 `run_agent_session`；下一轮从磁盘中的项目继续。外层按 `max_iterations` 检查会话轮数，默认值 `None` 允许无限运行。因此直接使用示例的默认值无法满足课程要求的重试上限。这个上限计的是会话，CAD 一件零件的修复预算须另行定义。[agent.py · 2502341，2025-11-26](https://github.com/anthropics/claude-quickstarts/blob/25023412396a0bd082d50b4b4f39a864d35a3a73/autonomous-coding/agent.py)

**作者声明·工程复盘。** 起初，编程 Agent 会因看见已有页面而宣布任务完成。作者让初始化会话把面向用户的功能写成带检查步骤和通过状态的清单；后续会话每次处理一个功能，先跑通基本路径，再更新进度、留下提交。进度文件与 Git 历史帮助新会话找到可恢复状态。[长任务实践，2025-11-26](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

**分析推断。** 同一方法可以在“修改右孔”时接受检验。恢复所需的最小材料包括上一版参数源文件、双方已确认的孔位、建议但尚未确认的尺寸，以及上一次测量结果。新建模失败后仍应能打开上一版。组会可讨论在一次进程内保存这些材料是否够用，以及是否需要演示重启后的恢复。

## 哪些决定交给模型，哪些可以由程序直接判断

**作者声明·工程方法。** Anthropic 区分预定义工作流和由模型选择下一步的工具循环。其典型 Agent 每步读取外界返回结果，可以暂停向人询问，也可因达到最大迭代数而终止。工具设计的官方案例从少量真实任务和工具原型开始，记录调用、时延和错误，检查容易混淆的参数和过长的返回数据，再用原任务重新评估。[Building effective agents，2024-12-19](https://www.anthropic.com/research/building-effective-agents) · [Writing effective tools，2025-09-11](https://www.anthropic.com/research/writing-tools-for-agents)

**分析推断·课程情境。** 下表用同一个偏置孔说明一轮决策。数值是示例输入，尚未作为本表的实测结果。

| 环境事件 | 给模型或用户的证据 | 能观察到的处理结果 |
|---|---|---|
| 用户说“孔向右移 5”，图中有两个孔，单位也未确认 | 列出两个孔的名称、位置，在当前视图标注；询问目标孔、坐标系和单位。用户回复单独记录 | 已确认参数再进入建模；仍缺条件时回到提问。可核查交付前是否有用户回复 |
| 引擎执行圆角时抛出异常 | 工具名、关联特征、输入半径、错误类型与异常摘要、失败阶段、剩余额度 | 模型可修改特征顺序或生成方法，再执行原验收项。若要改变已确认半径，先请求用户决定 |
| 进程成功，孔心实测 X=20 mm，要求 X=25±0.1 mm | 标明坐标基准、目标、实测、带符号偏差 −5 mm、几何版本和检查项；可另附定位图 | 程序判定超差，模型可检查偏置或变换方向；重建后同时复测孔心和未改的孔径。预算耗尽时保留失败记录 |
| 程序超时或持续修不好 | 附超时阶段、尝试次数、最后成功版本以及最后一轮测量 | 调度器结束本次执行，区分“未生成”“生成但不合格”“通过”；下一条用户消息可决定如何继续 |

工作流较固定时，各阶段和停止原因容易回放；允许模型选择检查工具时，则可处理事先未想到的定位问题，同时需要记录它读过哪些几何信息。若引入规划、执行和视觉检查等多个角色，比较其价值可用同一批任务测误判、耗时和修复次数。哪种方式符合四人团队的开发周期仍待讨论。

## 评估既看对话，也读最终实体

**作者声明·官方评估实践。** Anthropic 把一次任务、一次尝试、完整交互记录、结束时的环境状态和评分程序分开。例如智能体称已订票时，要去系统里查预订是否实际存在。其 Claude Code 案例从内部使用反馈扩展到具体行为的回归测试。作者指出多次运行能暴露波动，能用程序验证的结果优先用确定性判据，同时给人工检查保留位置。[Demystifying evals for AI agents，2026-01-09](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**分析推断。** 课程可对同一运行做三次核对。先读对话，查看关键缺项是否真的得到确认。再对最终几何按预写容差独立测量，检查改动值和应保留值。最后重开 STEP、关联本次源文件与前后视图，核对交付是否可重现。把程序异常与几何超差分别计数，有助于判断后续应改工具实现、模型提示或验收逻辑。外观是否像支架可由人判断，孔心偏差则可直接从数值评分。

| 一次尝试至少保留的内容 | 复盘时能回答的问题 |
|---|---|
| 需求与确认消息、基准、单位、容差、零件与版本标识 | 哪个参数由用户确定？哪一个仍只是建议？ |
| 模型标识、SCA 版本、配置、提示词和工具版本、源文件与复现命令 | 换一台机器能否重建同一组几何？模型服务和工具是否发生变化？ |
| 工具输入和返回、耗时、错误种类、修复次数及其上限 | 哪一步开始偏离？预算在模型调用还是几何运行时耗尽？ |
| 测量对象、目标、实测、偏差、STEP 与前后视图、终止原因 | 只是能打开，还是每项几何条件均通过？修改是否连带改变了别处？ |

若对同一需求重复尝试，分别报告首次成功数、经修复成功数、总尝试数及耗时；三种结构各跑一次能展示覆盖面，样本量不足以估计上线后的稳定性。对受限执行也应分开验证：宿主能否强制结束超时任务，子进程能否超出允许运行的目录或取得无关凭据。上述条目是待验证问题；进程超时和文件系统隔离需要各自的证据。

## 多人使用 AI 编程工具时，交接什么

| 一手案例 | 作者报告的实际做法 | 对本课程可检验的启发（分析推断） |
|---|---|---|
| OpenAI 团队使用 Codex，从空仓库开发内部产品；早期三名工程师驱动工作，后续扩至七人。**作者声明**，属于内部复盘 | 每个 Git worktree 可单独启动应用并读取自己的日志；短入口文件指向版本化项目知识；人类把反复出现的评审意见变成可检查规则。[工程复盘，2026-02-11](https://openai.com/index/harness-engineering/) | 交接一个孔位回归问题时，一并给出输入、源文件版本、测量命令和期望结果。另一位同学能否在自己的环境复现，比提交多少行代码更能判断交接是否充分 |
| Anthropic 研究员用多实例 Claude Code 并行写 C 编译器。**作者声明**，是一名研究员协调多个实例的实验 | 各实例有自己的工作副本，用共享仓库的任务文件避开重复认领，以编译测试判断进展；作者专门指出合并冲突仍十分频繁。[实验记录，2026-02-05](https://www.anthropic.com/research/building-c-compiler) | 对已能分开的任务，约定输入输出和对应测试可减少重做。若工具输出、测量和会话标识仍待共同确定，先用同一个零件跑通接口更容易暴露不一致 |

两篇复盘记录了不同组织条件下的实践，都没有测量四人 CAD 课程团队的净收益。组会可先挑一个真实交接场景，例如“同学仅凭运行目录能否解释孔位为什么出错”，再决定哪些日志、版本信息和交接约定值得投入时间。
